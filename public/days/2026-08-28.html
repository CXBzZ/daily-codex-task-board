## 行业是什么，为什么小众 今天选择的行业是：面向海外小型 SaaS、开发者工具、开源项目、B2B 微型团队和独立软件产品的 Release Notes / Changelog 整理、GitHub Releases 发布 QA 与多渠道产品更新服务。 它不是泛泛的技术文案，也不是替客户写营销软文。更准确地说，它把工程团队的 PR、issue、commit、Linear/Jira ticket、产品经理粗稿、客服反馈和演示录屏，整理成用户能读懂、开发者能追踪、销售/客服能转述的发布说明。典型交付包括：CHANGELOG.md、GitHub Release 草稿、短版 in-app announcement、邮件/Slack 摘要、迁移注意事项、breaking changes 标记、贡献者署名检查、截图/链接 QA、发布前敏感信息检查和发布后归档 SOP。 它小众，是因为需求夹在产品运营、技术写作、版本管理、开源协作、客户沟通和工程流程之间。小团队经常会发版，但发布说明容易变成 raw git log，或者只写给内部工程师看；产品经理懂用户语言但未必会读代码 diff；工程师知道改了什么但不一定愿意整理“哪些变化对用户重要”。Keep a Changelog 的核心原则之一就是 changelog 是给人看的，记录 notable changes，而不是机械堆 commit。AI 可以起草，但仍需要人判断取舍、分组、解释影响和删除不应公开的信息。 ## 目标市场 本期选择：中国境内可做的海外市场，重点是英语 SaaS、开源工具、API/SDK、开发者工具、AI 工具、小型 B2B 软件和插件生态。 潜在客户包括 1-20 人 SaaS 团队、独立开发者、开源商业化项目、Chrome/VS Code/Figma/Shopify/WordPress 插件作者、API/SDK 提供商、技术型 agency、产品营销顾问和客户成功团队。中国境内个人、个体工商户或一人公司可以通过 Upwork、Fiverr、GitHub/LinkedIn、开源社群、Product Hunt/Indie Hackers、开发者工具社群和代理白标分包获客，远程交付 Markdown、GitHub Release 草稿、产品更新页面草稿、邮件摘要和 QA checklist。 为什么适合 OPC/一人公司或数字游民验证：固定资产轻，主要需要英文技术写作、GitHub/GitLab 基础、版本号常识、产品理解、截图和异步沟通；不需要海外实体门店、不需要当地强牌照、不处理实物库存。新手可以从“一个小版本/一个功能的 release note cleanup”或“把 10-20 个 PR 整理成 changelog 草稿”的小单验证。 ## 典型需求场景和客户是谁 1. 小型 SaaS 每周或每两周发版，但 release notes 长期拖欠，需要把多个版本补成可读的 changelog。 2. 开源工具维护者有 GitHub 自动生成 release notes，但需要人工检查分类、breaking changes、贡献者署名、依赖升级和安全敏感内容。 3. API/SDK 团队发布新版本，需要把 SemVer、兼容性、迁移步骤、弃用字段和示例链接写清楚。 4. B2B 产品团队要把工程 ticket 转成客户成功、销售和用户都能使用的短版产品更新。 5. 插件/扩展作者要在 GitHub Releases、CHANGELOG.md、官网 update page、邮件和 Slack/Discord 社群同步一版一致口径。 6. 技术文档 agency 或产品营销顾问已有客户关系，但不想逐周整理工程变更，可以把发布说明整理分包给远程服务者。 ## 行业如何运作，典型参与方和工作流 典型参与方包括创始人、产品经理、工程师、DevRel、技术写作者、客户成功、开源维护者、GitHub/GitLab、Linear/Jira、LaunchNotes/Beamer/Headway 类产品更新工具、邮件/Slack/Discord 渠道和最终用户。 典型工作流： 1. 预筛选：确认客户有权提供仓库、ticket、录屏和用户反馈；拒绝未授权私有代码、泄露漏洞细节、伪造用户评价、未公开融资/并购/客户名单、夸大功能能力和欺骗性宣传。 2. 授权和范围：用平台订单或英文 SOW 写清版本范围、来源材料、是否只读、是否可创建 draft、是否包含截图、是否发布到生产渠道、返修轮次、保密、删除确认和不承诺项。 3. 素材收集：读取 merged PR、issue、release draft、tag diff、Linear/Jira ticket、产品经理 notes、demo 视频和客服反馈；只拿最小必要权限。 4. 信息筛选：区分 user-facing、developer-facing、internal-only、dependency/noise、security-sensitive 和 breaking changes；删除不应公开的内部链接、客户名、密钥、漏洞利用细节和未确认承诺。 5. 结构化写作：按 Added、Changed、Deprecated、Removed、Fixed、Security 或产品自定义分类整理；对 API/SDK 项目注明 SemVer、迁移提醒、兼容性和示例链接。 6. 多渠道改写：长版 CHANGELOG.md、GitHub Release、中版产品更新页、短版邮件/Slack/in-app notification 分别适配语气和长度，避免多处口径冲突。 7. 发布前 QA：检查版本号、tag、日期、链接、截图、贡献者署名、issue/PR 引用、截图里是否有敏感信息、是否把 beta/preview 写成 GA。 8. 交付和归档：交付 Markdown/HTML/平台草稿、变更来源表、已删敏感项、待客户确认问题、下次发版 checklist 和模板。 官方资料支撑这些工作流的真实性：GitHub Docs 说明 release 可打包软件、release notes 和二进制文件，并基于 git tags；GitHub 自动生成 release notes 会列出 merged PR、contributors 和 full changelog link，但也提醒发布前检查生成内容是否只包含应包含的信息。Keep a Changelog 2.0 明确 changelog 是面向人的 notable changes 记录，release notes 是单次发布公告，二者相关但不相同；它也提醒 LLM/自动化可用于起草，但人仍要判断什么值得写、如何分组、怎样面向读者表达。SemVer 则为 API/SDK 类项目提供 MAJOR.MINOR.PATCH 的兼容性语义。 ## 中国境内承接海外市场的执行细节 跨境获客：平台获客要遵守 Upwork/Fiverr 站内沟通、付款和反绕单规则；GitHub/LinkedIn 冷启动应展示公开样例，不抓取邮箱群发。对开源项目可先做公开 issue/PR 的示范性 rewrite，但不要未经邀请提交带商业导流的垃圾 PR。 远程交付：优先只读权限、客户导出的 PR/ticket 列表、release draft 和录屏。需要进入私有仓库、Linear/Jira、LaunchNotes、Beamer 或 Slack 时，使用临时最小权限账号；若要发布到公开渠道，必须让客户最终确认或由客户自己点击 publish。 合同、发票与收款：平台单按平台合同、托管和账单走；独立客户用英文 SOW，写清版本范围、源材料、交付格式、渠道、是否只做 draft、客户最终审核责任、保密、删除确认、付款节点和不提供法律/安全披露/投资者关系意见。收款可用平台托管、Payoneer、Wise Business、PayPal 或银行跨境收款等合规路径，取决于主体、平台支持地区和银行要求。 税务申报：中国境内个人或一人公司承接海外服务，应保留合同、平台账单、收款流水、结汇记录、交付稿和工具费用凭证。个人劳务、个体工商户、个人独资企业和有限公司的增值税、个税、企业所得税、成本扣除和发票口径不同；跨境服务是否适用免税政策，要按具体服务性质、客户所在地和主管税务机关判断。 外汇与结算：真实、合法的服务贸易/经常项目收入通常要配合银行真实性审核。国家外汇管理局资料要求个人外汇业务按交易性质管理，银行审核材料真实性，不得分拆或使用虚假单证规避管理。因此不要用地下钱庄、虚假贸易、代收代付或拆分结汇处理收入。 平台规则：遵守 GitHub/GitLab、Upwork、Fiverr、Slack/Discord、LaunchNotes/Beamer 等平台规则。不得诱导站外付款规避平台，不得发布恶意代码、泄露 token、伪造贡献者、刷评价、冒充客户或平台官方。 数据/隐私合规：release 素材可能包含客户名、用户邮箱、工单截图、崩溃日志、内部 URL、API key、未公开漏洞和商业路线图。服务者应尽量使用脱敏材料；涉及个人信息或商业敏感信息时，签 NDA/DPA、限制下载、本地加密、交付后删除。若素材涉及中国境内个人信息向境外提供，或境外客户数据进入中国后再回传，也要关注《个人信息保护法》和《促进和规范数据跨境流动规定》的告知、同意、标准合同/认证/安全评估等边界。 语言和时区门槛：需要用英文和客户确认 tone、audience、breaking change、known issue、beta/GA、deprecation、migration 和 security-sensitive 的边界。美国客户可能要求中国早晚沟通；可用异步问题表、评论模式和固定交付窗口降低时区压力。 ## 为什么适合或不完全适合 OPC/一人公司 适合点：单人能完成素材整理、英文改写、Markdown、GitHub draft、发布前 QA 和模板维护；固定资产轻，项目可以从一个小版本切入；交付物清晰，容易产品化为“release notes cleanup”“monthly changelog maintenance”“GitHub Release QA”。 不完全适合点：复杂 API/SDK、大企业安全公告、法律披露、上市公司投资者关系、重大事故复盘和多语言全球发布需要专业团队、律师/安全团队和客户内部审批。OPC 应控制在草稿、QA 和流程整理，不做未经授权的最终公开发布。 ## 为什么适合或不完全适合数字游民/远程工作者 适合点：核心工作依赖电脑、英文、仓库/ticket 只读权限和文档工具，天然可远程；成果是文本和 QA 表，适合异步交付；可与技术文档、帮助中心、开源维护、DevRel 内容和产品营销组合销售。 不完全适合点：需要稳定网络、安全设备和安静沟通环境；私有仓库和未公开路线图不适合在公共 Wi-Fi 或共享电脑上处理。旅居会影响平台 KYC、收款账户、税务居民身份和客户会议时间。 ##
